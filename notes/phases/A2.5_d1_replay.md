## 7. Source review of the shared native path (9 October)

Claude read the wrapper (`native/se_llama.cpp`) and the pinned llama.cpp b11277 sources (`src/llama-batch.cpp`,
`src/llama-context.cpp`, `src/llama-kv-cache.cpp`, at tag b11277 of github.com/ggml-org/llama.cpp). **No concrete defect
was found.**

- **Cache removal.**
  - `se_eval` checks `keep` against the cached count, and when `keep` is lower calls
    `llama_memory_seq_rm(memory, 0, keep, -1)`. It refuses if that fails.
  - The cached count is `llama_memory_seq_pos_max(memory, 0) + 1`.
- **Positions.** The wrapper passes `llama_batch_get_one` batches without positions. llama.cpp then gives each token the
  sequence's last cached position plus one (`llama-batch.cpp`, line 1264), so after a removal at `keep`, the next token
  is at position `keep`.
- **Batch boundaries.** Tokens go in chunks of 512 (`n_batch` = `n_ubatch` = 512), so U, R and P compute the final token
  in batches of different sizes:
  - U evaluates the request in chunks from position 0;
  - R evaluates the last token alone;
  - P splits the final chunk at the command line: the prefix, then a suffix of 17 to 20 tokens.
- **Final logits.**
  - With no logit flags, only each batch's last token is an output (`llama-batch.cpp`, lines 1308–1311).
  - `llama_get_logits_ith(ctx, -1)` returns the latest decode's last output (`llama-context.cpp`, lines 916–917), which
    is the request's final token.
  - The wrapper copies the whole row and its log-sum-exp.
- **KV cells and attention span.**
  - A removal frees the cells and moves the insertion head back to the first freed cell (`llama-kv-cache.cpp`,
    `seq_rm`).
  - Attention spans the highest used cell, rounded up to 256 (`get_n_kv`).
  - In this single-sequence schedule, U, R, P and U' therefore use the same positions, the same cells and the same span.
- **Configuration.**
  - The runtime's own lines report qwen2, 24 layers, 14 heads, 2 KV heads, head size 64, embedding 896, feed-forward
    4,864, RMS epsilon 1e-6, rope base 1,000,000 (type 2), trained context 32,768, vocabulary 151,936 and file type
    Q8_0.
  - The model description pins the checkpoint (`7ae5576…`), 24 layers, 2 KV heads, head size 64 and the vocabulary.
    Those agree.
- **Missing evidence:**
  - The GGUF export record (the converter run and its source snapshot) lives in the git-ignored model folder and was not
    inspected.
  - Hidden size, head count, feed-forward size, RMS epsilon and rope base are not pinned in the repository, so they were
    compared only with the runtime's report.
  - Which CPU kernels ran for each batch size, and how they accumulate, was not instrumented. That the final token's
    arithmetic differs with batch size is expected in kind from the code paths; its size is not established by
    reading.

What the review supports:

- Positions, cache removal and final-row selection behave as intended for the U/R/P schedule.
- It does not establish why path and platform differences are as large as observed.
- It leaves the next diagnostic informative. Positions, cells and spans are identical, so U' against U tests
  context-history dependence, and repeats test repeatability.
