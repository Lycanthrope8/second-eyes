# A2.5 delivery 3: the cache manager and the interactive pipeline

Status: **built and tested here; not yet run on the headset.**

- It builds on delivery 2, which is closed: the headset's prompt builder (D104).
- Delivery 1's replay acceptance remains failed, so the cache is a switch, off by default (section 2).

## 1. Scope (D98, D99(6))

On the headset, a request (a versioned annotated snapshot and a typed command) becomes a structured outcome: a target
object, or ASK. The pipeline is one place that every intake uses.

- The panel's check uses it now.
- Delivery 4's presets and ADB inbox will hand it the same request type, so the intakes cannot behave differently.
- Delivery 4 also adds the interactive UI: target highlight, cancel, and the outcome shown to the user.
- Delivery 5 measures it.

## 2. Design

**The request** (`InteractiveRequest`) holds:

- the snapshot's ID and the SHA-256 of its file;
- the scene and command records as JSON text;
- its source.

**Checks before any evaluation.** A request is refused, with a reason, when:

- its scene text is not the registered snapshot (`snapshot_hash_mismatch`);
- its command names another scene or revision (`stale_scene`);
- its records are malformed (`invalid_input`);
- its prompt would not fit the context with one continuation position (`context_budget_exceeded`, 8,192 tokens).

**The prompt.** Delivery 2's verified core builds the document, the serialized-order mapping (D104) and the prompt. Their
hashes are recorded.

**The cache** (`PrefixCache`) bookkeeps the one cached sequence: its tokens and the snapshot they belong to. The mode is
a switch:

- **Off** (the default): every request is evaluated in full. That is the replay's U path.
- **ExactPrefix:** keep the longest common token prefix with the previous request on the same snapshot, at most n − 1,
  so the final position is always evaluated.
  - Another snapshot (an inventory or scene change) invalidates the cache entirely.
  - A pose or command change keeps only the prefix before it. That follows D99(6): choices come before the scene, so the
    inventory-dependent part leads the prompt.
  - A failed evaluation, or a cache that does not hold the expected positions afterwards, resets it.

ExactPrefix is the P path of delivery 1's replay. Its numerical acceptance is delivery 1's open question: R/U and P/U fail
D101. Turning it on for interactive use is the project lead's decision. Every outcome records the cache mode and the
tokens kept and evaluated.

**Scoring** is the replay's: offered letters only, exact ties at the top go to K, and a non-finite output is a failed
outcome, never a choice.

**The outcome** (`InteractiveOutcome`) has a status, plus its details:

| Status | Meaning |
|---|---|
| `completed` | a target object |
| `ask` | the model chose ASK, or the top offered scores tied |
| `refused` | with a reason |
| `failed` | with a reason |
| `cancelled` | before evaluation |

It carries the offered logits, shares and log-probabilities, the margin, and the time of each stage (build, tokenize,
evaluate, score, total). The pipeline never throws: every way out is a structured outcome.

## 3. On the headset

`InteractiveRunner` loads the model once with the accepted settings: 8,192 tokens, 2 threads, flags 0. It runs the
pipeline on the worker thread and appends each outcome as it completes.

**Interactive check (A2.5 d3)** is a new button beside Replay and Golden check. It sends the 32 verified golden requests,
read through the golden check's hash-checked reader, through the pipeline twice: cache off, then exact prefix. It writes
`files/interactive/results/<UTC time>/`:

- `identity.json`;
- `outcomes-off.jsonl` and `outcomes-prefix.jsonl`;
- `done.json`, written last, with:
  - the prompts equal to the goldens;
  - the choices equal with and without the cache;
  - the offered logits identical with and without the cache;
  - the requests on which the cache reused tokens.

Its events are `interactive.start`, `interactive.outcome` (one per request) and `interactive.end`.

On the laptop, `python -m grounding.quest interactive-pull --run RUN` brings the newest finished folder and its event
log into `raw/interactive/`.

**Expected duration**, from r009's headset replay (a median of 19.8 seconds per full evaluation, about 114 tokens a
second):

- about 11 minutes without the cache;
- about 3 minutes with it;
- about 15 minutes in all.

The headset should stay awake throughout, so wear it.

## 4. Testing here

- **The pure core on .NET 8, at C# 9,** with a labelled fake native and the real goldens and asset: 13 checks.
  - The pipeline builds all 32 golden prompts and mappings exactly.
  - Cache off evaluates in full.
  - ExactPrefix keeps n − 1 for a repeat and exactly the shared prefix for another command or pose (to the token), and
    nothing for another snapshot.
  - The refusals: hash mismatch, stale scene, context ceiling.
  - A failed evaluation resets the cache.
  - An exact tie is ASK with no target.
  - Cancellation stops before evaluation.
  - A non-finite row fails.
  - The outcome's JSON.
- **The Unity glue** type-checks against stubs with the rest of the runtime, replay and prompting code: 0 errors, 0
  warnings. `ChatPanel.cs` is checked by Unity's compile.
- **The laptop's pull,** on a labelled fake device: 3 checks.
  - The folder lands in `raw/interactive` with its event log.
  - The receipt counts each pass's statuses and reused tokens.
  - A missing folder is refused.
