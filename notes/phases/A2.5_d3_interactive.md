## 1. Scope (D98, D99(6))

On the headset, a request (a versioned annotated snapshot and a typed command) becomes a structured outcome: a target
object, or ASK. The pipeline is one place that every intake uses.

- The panel's check uses it now.
- Delivery 4's presets and ADB inbox will hand it the same request type, so the intakes cannot behave differently.
- Delivery 4 also adds the interactive UI: target highlight, cancel, and the outcome shown to the user.
- Delivery 5 measures it.

## 2. Design

**The request** (`InteractiveRequest`) holds:

- the snapshot's ID and the SHA-256 of its file;
- the scene and command records as JSON text;
- its source.

**Checks before any evaluation.** A request is refused, with a reason, when:

- its scene text is not the registered snapshot (`snapshot_hash_mismatch`);
- its command names another scene or revision (`stale_scene`);
- its records are malformed (`invalid_input`);
- its prompt would not fit the context with one continuation position (`context_budget_exceeded`, 8,192 tokens).

**The prompt.** Delivery 2's verified core builds the document, the serialized-order mapping (D104) and the prompt. Their
hashes are recorded.

**The cache** (`PrefixCache`) bookkeeps the one cached sequence: its tokens and the snapshot they belong to.

- **Off,** the default for development and the only mode for operational requests: every request clears the prior KV
  state (keep 0) and evaluates its complete prompt. That is the replay's U path. The positions cached afterwards must
  equal the prompt's length.
- **ExactPrefix,** for diagnostic execution only (`ExecutionPurpose.Diagnostic`): keep the longest common token prefix
  with the previous request on the same snapshot, at most n − 1. That is the replay's P path.
  - Another snapshot invalidates the cache entirely.
  - A pose or command change keeps only the prefix before it.
  - A failure resets it.
- **An operational request with ExactPrefix** is refused before any evaluation, as `prefix_reuse_not_accepted`.

**The earlier finding, stated precisely.** On the headset (r009), the P/U comparison failed D101 on 10 of 41 requests,
about a quarter. A D101 failure is a failure of a TVD, ranking or best-candidate criterion, and it does not mean the
selected target changed:

| | Comparison | Failed D101 | Selected code changed |
|---|---|---|---|
| Headset (r009) | P/U | 10 of 41 | 2 (r0001, r0329) |
| Headset (r009) | R/U | 11 of 41 | 1 (r0329) |
| Desktop (r010) | P/U | 9 of 41 | 3 (r0001, r0329, r0344) |
| Desktop (r010) | R/U | 11 of 41 | 3 |

**Every outcome records the execution that actually ran:**

- `purpose`: operational or diagnostic;
- `cache_mode`;
- `execution_path`:
  - `U`: prior KV cleared, complete prompt;
  - `P`: a cached prefix kept;
  - `none`: no evaluation;
- `prior_cached_tokens`;
- the tokens kept and evaluated.

**Scoring** is the replay's: offered letters only, exact ties at the top go to K, and a non-finite output is a failed
outcome, never a choice.

**ASK and failures are kept apart.** An ASK records its basis:

- `model_selected`: K had the top offered score;
- `exact_tie`: the protocol's tie rule.

Technical failures (tokenization, evaluation, a cache mismatch, a non-finite row) are `failed` outcomes with their
reasons, never an ASK. Configuration problems are `refused`, with their reasons.

**The outcome** (`InteractiveOutcome`) has a status, plus its details:

| Status | Meaning |
|---|---|
| `completed` | a target object |
| `ask` | the model chose ASK, or the top offered scores tied |
| `refused` | with a reason |
| `failed` | with a reason |
| `cancelled` | before evaluation |

It carries the offered logits, shares and log-probabilities, the margin, and the time of each stage (build, tokenize,
evaluate, score, total). The pipeline never throws: every way out is a structured outcome.

## 3. On the headset

`InteractiveRunner` loads the model once with the accepted settings: 8,192 tokens, 2 threads, flags 0. It runs the
pipeline on the worker thread and appends each outcome as it completes.

**Interactive check (A2.5 d3)** is a new button beside Replay and Golden check. It is diagnostic execution. It sends the 32 verified golden requests, read through the golden check's hash-checked
reader, through the pipeline twice: cache off (path U), then exact prefix (path P after each snapshot's first request). It writes
`files/interactive/results/<UTC time>/`:

- `identity.json`;
- `outcomes-off.jsonl` and `outcomes-prefix.jsonl`;
- `done.json`, written last, with each pass's statuses, ASK bases and execution paths, and:
  - the prompts equal to the goldens;
  - the choices equal with and without the cache;
  - the offered logits identical with and without the cache;
  - the requests on which the cache reused tokens.

Its events are `interactive.start`, `interactive.outcome` (one per request) and `interactive.end`.

On the laptop, `python -m grounding.quest interactive-pull --run RUN` brings the newest finished folder and its event
log into `raw/interactive/`.

**Expected duration**, from r009's headset replay (a median of 19.8 seconds per full evaluation, about 114 tokens a
second):

- about 11 minutes without the cache;
- about 3 minutes with it;
- about 15 minutes in all.

The headset should stay awake throughout, so wear it.

## 7. ChatGPT's review of r016 (10 October) and two reliability corrections

**The review.** The tested functional path passes, and r016 is preserved. Uncached U stays the development default and
prefix reuse stays diagnostic only. Numerical acceptance remains unresolved.

**Correction 1: failure handling in the shared pipeline.**

- **Before:** `Pipeline.Run` committed the cache before scoring, and a scoring failure returned without resetting it.
  Exceptions from the native calls could escape the pipeline.
- **Now:**
  - tokenization, evaluation and scoring each have an explicit failure boundary (`tokenization_exception`,
    `eval_exception`, `scoring_exception`);
  - every evaluation or scoring failure resets the cache;
  - the cache is committed only after valid scoring;
  - no failure becomes an ASK.
- **Tests:** five added. Each exception becomes an explicit failure, and the next request recovers. After a
  non-finite row the next request keeps 0 tokens, not n − 1.

**Correction 2: D104's startup check before serving.**

- **Before:** the interactive check and the session read the goldens with hash checks only.
- **Now:** `StartupGuard` runs once after the model loads, before any request:
  - the five prompt self-checks;
  - the reconstruction of every golden: document, mapping, mapping hash, prompt and native token IDs.

  Any failure refuses processing. The interactive check returns a refusal with nothing evaluated. The session refuses
  to start, and the panel's failure path ends it. The result is recorded in `identity.json`, in `session.json` and as
  an `interactive.startup_check` event.
- **Tests:** four added:
  - the real goldens pass, with 5 of 5 self-checks and 32 of 32 goldens;
  - one wrong native token refuses, naming the golden;
  - a throwing tokenizer refuses;
  - the record is checked.

The C# checks are now 45 in all. The corrections reach the headset at the next Unity build. No headset run is needed for
them.

ChatGPT's A2.5 review examined `bbb0ffe`, from before these corrections, and asked for the same two. Both were already
in `e8e052d`. The review's wording also covers two edges, now hardened:

- `Pipeline.Run` has a top-level boundary: anything the stage boundaries do not anticipate is `failed`
  (`pipeline_exception`), and resets the cache;
- the interactive check's runtime call answers an exception as `failed` (`runtime_error`), as the session's does.
